# Step 10: Deployment and Final Documentation

## Deployment configuration

PaperLoop is prepared for Render as a Django WSGI service backed by Render PostgreSQL. The infrastructure declaration is `render.yaml`; Render's Blueprint links `DATABASE_URL` to the database's internal connection string. Render recommends the internal URL when the app and database share a region because it uses the private network and avoids external routing ([Render PostgreSQL connection guide](https://render.com/docs/postgresql-creating-connecting)).

The web build installs `requirements.txt`, collects static assets, and applies migrations. WhiteNoise serves collected static files, and Gunicorn serves `config.wsgi:application`. In production, Django requires an explicit secret key, turns on secure session and CSRF cookies, trusts Render's HTTPS proxy header, and redirects HTTP to HTTPS. Set the host and CSRF origin variables to the actual service/custom domain.

### Render setup and release

1. Push the repository to the Git provider and connect it to Render.
2. Create a new Blueprint deployment from `render.yaml`. Review the resources and plans before confirming creation.
3. Wait for build and deployment. The build applies migrations before Gunicorn starts.
4. Create an administrator in Render Shell: `python manage.py createsuperuser`.
5. Check the service URL, `/admin/`, dashboard behavior, and CSS/static assets. For a custom domain, update `DJANGO_ALLOWED_HOSTS` and `DJANGO_CSRF_TRUSTED_ORIGINS` in Render and redeploy.
6. Before a real pilot, select a persistent paid Postgres plan, configure backups/retention for the chosen service tier, and verify restore procedures. The checked-in Blueprint uses free plans only to support a no-cost demo; do not store important pilot or production data there. Confirm Render's current plan limits and pricing before provisioning.

### Environment variables

| Variable | Render value | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | Blueprint reference to `paperloop-db` internal connection string | PostgreSQL connection; credentials stay in Render |
| `DJANGO_SECRET_KEY` | Generated by Render | Django signing secret |
| `DJANGO_DEBUG` | `false` | Enables production security settings |
| `DJANGO_ALLOWED_HOSTS` | `paperloop.onrender.com` | Accepted HTTP host header |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | `https://paperloop.onrender.com` | Trusted HTTPS origin for form submissions |

Do not commit populated `.env` files or production credentials. `.env.example` contains local placeholders only. For local development, the existing `DB_*` settings remain available; `DATABASE_URL` takes precedence.

## Project evaluation summary

PaperLoop is a Django marketplace prototype for educational institutions and recycling partners. It includes organization registration and role-based access, admin verification, paper listings, partner discovery and recommendations, collection scheduling/completion, transaction history, and digital recycling records. PostgreSQL is the intended operational database. The `ml_engine` package provides prototype forecasting, ranking, and bulk aggregation; its included datasets and labels are synthetic.

### Known limitations and release gates

- Test and smoke-check results are existing Step 9 evidence, not a fresh run against Render.
- There is no live deployment URL or verified cloud database in this repository state.
- Pilot data and model evaluation are synthetic; no real-world predictive quality claim is supported.
- The current Blueprint's free database is for a disposable demonstration. Persistent pilot data requires a suitable paid plan and an operational backup/restore process.
- Organization verification policy and environmental impact assumptions require stakeholder approval before external use.
- User-uploaded listing images use local `MEDIA_ROOT`; Render's filesystem is not a durable cross-deploy media store. A real pilot should configure object storage or another persistent media service before relying on uploads.
- `requirements.txt` includes PyTorch, NumPy, and pandas; cold builds can take longer and use more memory than a basic Django service. Check deployment logs and select a web plan with adequate build/runtime resources if needed.
